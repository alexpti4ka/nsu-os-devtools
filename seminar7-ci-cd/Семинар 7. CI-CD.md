# Семинар 7. CI/CD — операция «Старт разрешён»

Штаб Evil Corp ждёт доклад о готовности к старту. Вы соберёте панель
Mission Control, настроите проверки в GitHub Actions и разберёте сбой
телеметрии. Опубликованная панель свяжет результат с вашим позывным,
конкретным запуском и историей исправления.

## Задача 1. Подготовьте репозиторий и панель

1. В своём аккаунте GitHub создайте публичный учебный репозиторий
   `mission-control`. При создании добавьте README, чтобы появилась
   ветка `main`.
2. В этом репозитории откройте **Settings → Pages → Build and deployment**
   и в поле **Source** выберите **GitHub Actions**. Сделайте это до
   отправки workflow. Выбирать предложенный шаблон публикации не нужно.
3. Склонируйте свой репозиторий. Из каталога с материалами скопируйте
   содержимое [demo-app](home_tasks/CI-CD-с-GitHub-Actions/demo-app/)
   в корень клона, включая скрытые `.github/` и `.gitignore`. Например,
   запустите из корня клона `cp -a /путь/к/demo-app/. .`, подставив
   фактический путь. Шаблон заменит стартовый README своим описанием.
4. В `data/mission.env` придумайте название миссии (`MISSION_NAME`) и
   запишите свой позывной из карточки Evil Corp (`CALLSIGN`). Поле
   `PR_NUMBER` пока оставьте пустым. Для этой работы достаточно позывного.
5. Выполните `make test check-data site report`. Откройте
   `site/index.html` локально. На странице должны быть видны миссия,
   позывной и телеметрия.

## Задача 2. Напишите два шага GitHub Actions

Откройте `.github/workflows/ci.yml`. В задании `verify` между
`Checkout code` и сборкой страницы есть место для двух шагов. Напишите
их сами, ориентируясь на соседние шаги. Для каждого нужны поля `name`
и `run`.

- `Run unit tests` выполняет `make test`.
- `Validate mission data` выполняет `make check-data`.

Проверьте отступы YAML. У обоих шагов должен быть такой же отступ, как у
шага сборки страницы. Перед отправкой объясните соседу, почему настройки
публикации находятся в отдельном задании `deploy` и зачем ему
`needs: verify`.

Закоммитьте стартовую версию и отправьте её в `main`. Во вкладке
**Actions** откройте первый запуск **Mission Control**. Найдите оба своих
шага и убедитесь, что они выполнены. Откройте опубликованную страницу из
задания `deploy` или из **Settings → Pages**. Это версия, которую увидят
пользователи, пока вы разбираете инцидент в отдельной ветке.

## Задача 3. Устройте инцидент и прочитайте лог

Создайте ветку `incident/oxygen-overload`. Поставьте `OXYGEN=120` в
`data/mission.env`, сделайте коммит, отправьте ветку на GitHub и откройте
pull request (PR) в `main`.

Дождитесь завершения запуска. В **Actions** откройте упавший шаг и
сравните его вывод с локальным `make check-data`. В описании PR оставьте
ссылку на красный запуск и коротко ответьте своими словами:

- На каком шаге произошёл сбой и какое правило нарушено?
- Почему модульные тесты прошли и какие шаги GitHub пропустил после сбоя?
- Что сейчас показывает опубликованная панель и почему?

## Задача 4. Исправьте данные и проверьте границы

Верните `OXYGEN` к допустимому значению, отличному от стартового `21`.
Добавьте в `tests/test_telemetry.c` две проверки. При нормальной
температуре оба граничных значения кислорода, `19` и `25`, должны
давать `GO`. Сохраните существующие проверки и диапазоны.

Запишите номер открытого PR в `data/mission.env`. Например, если адрес
PR заканчивается на `/pull/3`, укажите `PR_NUMBER=3`. По этому номеру
панель построит ссылку на историю инцидента.

Выполните `./check.sh` из корня репозитория. Одним коммитом добавьте
исправление, номер PR и новые тесты. Отправьте коммит в ту же ветку и
дождитесь зелёного запуска. Добавьте ссылку на него в описание PR рядом
со ссылкой на красный запуск. Описание можно изменить на GitHub без
нового коммита.

## Задача 5. Опубликуйте и проверьте результат

1. Слейте зелёный PR в `main`. Откройте **новый** запуск для `main` и
   проверьте, что `verify` и `deploy` завершились успешно.
2. На странице запуска в разделе **Artifacts** скачайте `mission-report`.
   Сверьте позывной, показания и SHA коммита в `mission-report.txt`
   с опубликованной панелью.
3. Обменяйтесь ссылками на панели с соседом. Проверьте, что позывной
   относится к автору работы, а обе ссылки на панели ведут в его
   репозиторий. По ссылке на PR найдите красный и зелёный запуски.

Сдайте **одну ссылку на опубликованную панель GitHub Pages**.
[Условия зачёта](home_tasks/CI-CD-с-GitHub-Actions/Задание.md).
