# CI/CD и GitHub Actions: теория к семинару

## Главная идея

**CI** (Continuous Integration) запускает сборку и автоматические проверки
после изменения кода. Это защита общей ветки: ошибка обнаруживается в том
коммите, который её внёс, а не через неделю перед сдачей проекта.

При **Continuous Delivery** проверенная версия готова к поставке, а
команда решает, когда её выпускать. При **Continuous Deployment**
публикация тоже происходит автоматически. На семинаре после успешной
проверки ветки `main` публикуется статическая страница GitHub Pages.

## Как устроен GitHub Actions

Workflow --- YAML-файл в `.github/workflows/`. Его основные части:

| Термин | Значение |
|---|---|
| workflow | весь процесс, описанный одним YAML-файлом |
| event | событие, например `push` или `pull_request` |
| job | набор шагов, выполняемый на одном runner |
| step | команда `run` или готовое действие `uses` |
| runner | временная виртуальная машина GitHub |
| artifact | файл, сохранённый после job для скачивания |
| deploy | публикация уже проверенного результата |

В Mission Control два задания. Шаги тестирования и проверки телеметрии
вы добавите сами.

```text
verify: checkout → test → validate data → build site → upload artifact
deploy: download artifact → pages upload → GitHub Pages
```

`deploy` зависит от `verify` через `needs: verify`. Если тест или проверка
данных вернули ненулевой код, `verify` завершается ошибкой, а деплой не
запускается.

## Почему нужен pull request

В `main` команда поддерживает рабочую версию. Изменение готовят в
отдельной ветке и открывают PR. Перед слиянием проверяют изменения и
результат CI. Защита ветки позволяет сделать проверку обязательной.

На этом семинаре красный запуск создаётся намеренно. Это не «плохая
оценка», а опыт диагностики: открыть упавший шаг, найти конкретное условие,
исправить причину, а не выключить тест.

## Артефакт и Pages --- разные результаты

- **Artifact** доступен в конкретном запуске Actions. Здесь это отчёт и
  собранная страница Mission Control; он нужен преподавателю и разработчику.
- **GitHub Pages** --- опубликованная версия сайта. Она показывает, что
  успешный `main` действительно дошёл до деплоя.

Не храните отчёт только на странице и не считайте артефакт деплоем: у них
разные роли.

## Что смотреть при красном CI

1. Откройте failed run во вкладке **Actions**.
2. Найдите первый упавший шаг: последующие часто пропущены как следствие.
3. Прочитайте последние строки лога и воспроизведите команду локально.
4. Исправьте причину в отдельном коммите.
5. Убедитесь, что следующий run зелёный; только затем делайте merge.
