# Семинар 6. Файловые системы Linux

## Цель семинара

На этом семинаре вы исследуете, как Linux представляет файлы и файловые системы:

- что такое inode;
- чем жёсткая ссылка отличается от символической;
- как несколько файловых систем образуют единое дерево каталогов;
- что происходит при монтировании;
- чем обычная файловая система отличается от `tmpfs` и `procfs`;
- как работает bind mount;
- как OverlayFS объединяет несколько слоёв;
- как эти механизмы применяются Docker.

Для некоторых заданий потребуются права суперпользователя.

> **Важно:** команды, изученные на предыдущих семинарах, приводятся в разделе **«Инструменты»** только как напоминание. Необходимые параметры следует искать самостоятельно через `man`.

## Задача 1. Исследуйте inode и ссылки

### Условие

В Linux имя файла и сам объект файловой системы — не одно и то же.

Запись каталога связывает **имя** с inode. Inode содержит метаданные объекта файловой системы: владельца, права доступа, временные метки, размер и информацию, необходимую для доступа к данным.

Имя файла непосредственно в inode не хранится.

Один inode может быть связан с несколькими именами через жёсткие ссылки.

Создайте рабочую директорию:

```bash
mkdir -p ~/seminar6/inodes
cd ~/seminar6/inodes
```

Создайте файл:

```bash
echo "Hello, filesystem!" > original.txt
```

Посмотрите его inode:

```bash
ls -li original.txt
```

и подробные метаданные:

```bash
stat original.txt
```

### Копирование

Создайте копию:

```bash
cp original.txt copy.txt
```

Сравните:

```bash
ls -li original.txt copy.txt
```

Ответьте:

- совпадают ли inode;
- являются ли эти файлы одним объектом;
- изменится ли `copy.txt`, если изменить `original.txt`.

Проверьте экспериментально.

### Жёсткая ссылка

Создайте:

```bash
ln original.txt hard.txt
```

Посмотрите:

```bash
ls -li original.txt hard.txt
```

и:

```bash
stat original.txt
```

Обратите внимание на поле:

```text
Links:
```

Измените данные:

```bash
echo "Changed through hard link" >> hard.txt
```

Посмотрите:

```bash
cat original.txt
```

Теперь удалите первоначальное имя:

```bash
rm original.txt
```

Проверьте:

```bash
cat hard.txt
```

Объясните, почему данные остались доступны.

### Символическая ссылка

Восстановите файл:

```bash
echo "Hello again" > original.txt
```

Создайте symbolic link:

```bash
ln -s original.txt symbolic.txt
```

Посмотрите:

```bash
ls -li original.txt symbolic.txt
```

и:

```bash
ls -l symbolic.txt
```

Определите, куда указывает ссылка:

```bash
readlink symbolic.txt
```

Удалите target:

```bash
rm original.txt
```

Попробуйте:

```bash
cat symbolic.txt
```

Объясните результат.

### Инструменты

`echo`, `ls`, `stat`, `cp`, `ln`, `readlink`, `rm`, `cat`

### Самопроверка

Вы должны уметь объяснить:

- почему `cp` создаёт новый inode;
- почему `ln` не создаёт новый inode для данных;
- почему hard link продолжает работать после удаления другого имени;
- почему symbolic link может стать «битой»;
- хранит ли inode имя файла.

Дополнительный вопрос:

> Почему жёсткую ссылку обычно нельзя создать между двумя разными файловыми системами?

## Задача 2. Исследуйте дерево монтирования и VFS

### Условие

Linux представляет разные файловые системы в виде одного дерева, начинающегося с:

```text
/
```

Для этого ядро использует слой **VFS — Virtual File System**, предоставляющий общий интерфейс для различных реализаций файловых систем.

Посмотрите статическую конфигурацию монтирования:

```bash
cat /etc/fstab
```

Теперь посмотрите, что смонтировано **прямо сейчас**:

```bash
findmnt
```

Сравните с:

```bash
mount
```

Исследуйте отдельные пути:

```bash
findmnt /
findmnt /proc
findmnt /dev
```

Определите файловую систему, содержащую конкретный файл:

```bash
findmnt -T /proc/cpuinfo
findmnt -T /etc/passwd
```

Посмотрите тип файловой системы:

```bash
df -T /
df -T /proc
df -T /dev
```

Исследуйте разрешение пути:

```bash
namei -l /etc/passwd
```

Если существует домашняя директория:

```bash
namei -l "$HOME"
```

### Обсудите

Почему:

```text
/etc/passwd
/proc/cpuinfo
/dev/null
```

выглядят как элементы одного дерева `/`, хотя находятся в файловых системах разных типов?

Почему вывод:

```bash
findmnt
```

может содержать значительно больше файловых систем, чем:

```bash
cat /etc/fstab
```

?

### Инструменты

`cat`, `findmnt`, `mount`, `df`, `namei`

### Самопроверка

Вы должны уметь объяснить:

- что такое mount point;
- чем `/etc/fstab` отличается от текущей таблицы mounts;
- для чего нужен VFS;
- почему разные файловые системы могут находиться внутри одного дерева каталогов.

## Задача 3. Исследуйте специальные файлы устройств

### Условие

В Linux часть объектов файловой системы представляет интерфейс не к обычным данным на диске, а к устройствам и драйверам.

Посмотрите:

```bash
ls -l /dev/null /dev/zero /dev/urandom
```

Обратите внимание на первую букву:

```text
c
```

Определите её значение через:

```bash
man ls
```

### `/dev/zero`

Получите 1 MiB данных:

```bash
dd if=/dev/zero of=zero1.bin bs=1M count=1
```

Затем 2 MiB:

```bash
dd if=/dev/zero of=zero2.bin bs=1M count=2
```

Сравните:

```bash
ls -lh zero1.bin zero2.bin
```

Но затем посмотрите:

```bash
stat /dev/zero
```

Ответьте:

> Если `/dev/zero` не содержит обычного файла размером несколько гигабайт, откуда берутся читаемые нули?

### `/dev/null`

Запишите:

```bash
echo "Hello world" > /dev/null
```

Теперь попытайтесь прочитать:

```bash
dd if=/dev/null bs=1 count=10
```

Ответьте:

- куда делись записанные данные;
- что возвращает `/dev/null` при чтении.

### `/dev/urandom`

Не выводите его содержимое через `cat`.

Получите небольшое количество данных:

```bash
dd if=/dev/urandom bs=16 count=1 2>/dev/null | od -An -tx1
```

Сравните несколько запусков.

### Инструменты

`ls`, `stat`, `dd`, `echo`, `od`

### Самопроверка

Объясните назначение:

- `/dev/null`;
- `/dev/zero`;
- `/dev/urandom`.

Что означает `c` в выводе `ls -l`?

### Очистка

```bash
rm -f zero1.bin zero2.bin
```

## Задача 4. Создайте файловую систему внутри обычного файла

### Условие

Создадим файл, который будет играть роль небольшого диска.

Перейдите:

```bash
mkdir -p ~/seminar6/loop
cd ~/seminar6/loop
```

Создайте файл размером 32 MiB:

```bash
dd if=/dev/zero of=disk.img bs=1M count=32
```

Посмотрите:

```bash
file disk.img
```

Создайте внутри файла файловую систему:

```bash
mkfs.ext4 disk.img
```

Снова:

```bash
file disk.img
```

### Подготовьте mount point

```bash
mkdir mnt_point
```

Создайте в обычной директории файл:

```bash
echo "I exist under the mount point" > mnt_point/hidden.txt
```

Посмотрите:

```bash
ls -la mnt_point
```

### Смонтируйте файловую систему

```bash
sudo mount -o loop disk.img mnt_point
```

Теперь:

```bash
findmnt -T "$PWD/mnt_point"
```

Посмотрите:

```bash
ls -la mnt_point
```

Что произошло с `hidden.txt`?

Создайте файл **внутри новой ФС**:

```bash
sudo sh -c 'echo "Stored inside ext4 image" > mnt_point/inside.txt'
```

Посмотрите:

```bash
ls -la mnt_point
```

### Loop device

Посмотрите:

```bash
losetup -a
```

Также:

```bash
lsblk
```

Найдите `/dev/loopX`, соответствующий `disk.img`.

### Размонтируйте

```bash
sudo umount mnt_point
```

Теперь:

```bash
ls -la mnt_point
```

`hidden.txt` снова появился.

Ответьте:

> Был ли `hidden.txt` удалён во время mount?

Снова смонтируйте:

```bash
sudo mount -o loop disk.img mnt_point
```

Проверьте:

```bash
cat mnt_point/inside.txt
```

### Инструменты

`dd`, `file`, `mkfs.ext4`, `mount`, `umount`, `findmnt`, `losetup`, `lsblk`

### Самопроверка

Объясните:

- что такое `disk.img`;
- для чего нужен loop device;
- что произошло с содержимым `mnt_point` после mount;
- где находится `inside.txt`;
- почему он сохраняется после `umount`/повторного mount.

### Очистка

```bash
sudo umount mnt_point 2>/dev/null || true
rm -rf mnt_point
rm -f disk.img
```

## Задача 5. Исследуйте tmpfs

### Условие

`tmpfs` — временная файловая система, данные которой хранятся в памяти, управляемой ядром.

Создайте:

```bash
mkdir -p ~/seminar6/ram_disk
```

Посмотрите память:

```bash
free -h
```

Смонтируйте `tmpfs`:

```bash
sudo mount -t tmpfs -o size=500M tmpfs ~/seminar6/ram_disk
```

Посмотрите:

```bash
df -h ~/seminar6/ram_disk
```

> `size=500M` задаёт максимальный размер файловой системы. Это не означает, что при mount сразу резервируется 500 MB RAM.

### Заполните tmpfs

```bash
dd if=/dev/zero \
   of=~/seminar6/ram_disk/file1.bin \
   bs=1M count=400
```

Проверьте:

```bash
df -h ~/seminar6/ram_disk
free -h
```

Теперь попробуйте создать ещё 200 MiB:

```bash
dd if=/dev/zero \
   of=~/seminar6/ram_disk/file2.bin \
   bs=1M count=200
```

Объясните ошибку.

### Размонтирование

```bash
sudo umount ~/seminar6/ram_disk
```

Смонтируйте снова:

```bash
sudo mount -t tmpfs -o size=500M tmpfs ~/seminar6/ram_disk
```

Посмотрите:

```bash
ls -la ~/seminar6/ram_disk
```

Где файлы?

### Инструменты

`free`, `mount`, `umount`, `df`, `dd`

### Самопроверка

Объясните:

- чем `tmpfs` отличается от ext4 на диске;
- означает ли `size=500M`, что сразу занято 500 MB RAM;
- почему данные исчезли после размонтирования.

### Очистка

```bash
sudo umount ~/seminar6/ram_disk
rmdir ~/seminar6/ram_disk
```

## Задача 6. Исследуйте procfs

`procfs` — виртуальная файловая система, через которую ядро предоставляет информацию о системе и процессах.

Определите filesystem:

```bash
findmnt /proc
```

Посмотрите CPU:

```bash
less /proc/cpuinfo
```

Память:

```bash
less /proc/meminfo
```

Попробуйте:

```bash
cat /proc/self/cmdline
```

Почему результат выглядит странно?

Посмотрите удобнее:

```bash
tr '\0' ' ' < /proc/self/cmdline
echo
```

### Процессы

Узнайте PID shell:

```bash
echo $$
```

Посмотрите:

```bash
ls /proc/$$
```

и:

```bash
cat /proc/$$/status
```

Сравните с:

```bash
ps -p $$
```

Ответьте:

> Где на диске хранятся данные `/proc/$$/status`?

### Инструменты

`findmnt`, `less`, `cat`, `tr`, `echo`, `ps`

### Самопроверка

Объясните:

- что такое procfs;
- почему `/proc` выглядит как обычная директория;
- что означает `/proc/<PID>`;
- создаются ли эти файлы как обычные файлы на диске.

## Задача 7. Создайте bind mount

### Условие

Bind mount позволяет сделать существующее поддерево файловой системы доступным ещё по одному пути.

Это **не копирование данных**.

Создайте:

```bash
mkdir -p ~/seminar6/bind/{bind_src,bind_dst}
cd ~/seminar6/bind
```

Запишите:

```bash
echo "My data" > bind_src/data.txt
```

Посмотрите:

```bash
ls -li bind_src/data.txt
```

Смонтируйте:

```bash
sudo mount --bind bind_src bind_dst
```

Проверьте:

```bash
ls -li bind_src/data.txt bind_dst/data.txt
```

и:

```bash
stat bind_src/data.txt
stat bind_dst/data.txt
```

Создайте:

```bash
touch bind_dst/new.txt
```

Теперь:

```bash
ls bind_src
```

Измените:

```bash
echo "Changed" >> bind_dst/data.txt
```

Проверьте:

```bash
cat bind_src/data.txt
```

Посмотрите mount:

```bash
findmnt -T "$PWD/bind_dst"
```

### Инструменты

`mount --bind`, `findmnt`, `ls`, `stat`, `touch`, `cat`

### Самопроверка

Объясните:

- почему inode в `bind_src` и `bind_dst` совпадает;
- почему новый файл появляется сразу с двух путей;
- копируются ли данные при bind mount.

### Очистка

```bash
sudo umount bind_dst
cd ..
rm -rf bind
```

## Задача 8. Соберите OverlayFS вручную

### Условие

OverlayFS создаёт объединённое представление нескольких слоёв.

Используем:

```text
lowerdir
upperdir
workdir
merged
```

Создайте:

```bash
mkdir -p ~/seminar6/overlay_test/{lower,upper,work,merged}
cd ~/seminar6
```

Создайте базовые данные:

```bash
echo "Base version" > overlay_test/lower/config.txt
echo "Only in lower" > overlay_test/lower/lower_only.txt
```

До mount:

```bash
find overlay_test -maxdepth 2 -type f -print
```

### Mount OverlayFS

```bash
sudo mount -t overlay overlay \
  -o lowerdir="$PWD/overlay_test/lower",upperdir="$PWD/overlay_test/upper",workdir="$PWD/overlay_test/work" \
  "$PWD/overlay_test/merged"
```

Посмотрите:

```bash
ls -li overlay_test/lower
ls -li overlay_test/upper
ls -li overlay_test/merged
```

Прочитайте:

```bash
cat overlay_test/merged/config.txt
```

### Измените файл через merged

```bash
echo "Changed version" | \
sudo tee overlay_test/merged/config.txt
```

Теперь:

```bash
cat overlay_test/lower/config.txt
cat overlay_test/upper/config.txt
cat overlay_test/merged/config.txt
```

Сравните inode:

```bash
ls -li overlay_test/lower/config.txt
ls -li overlay_test/upper/config.txt
ls -li overlay_test/merged/config.txt
```

### Что произошло

При первой записи в файл, существующий только в `lowerdir`, OverlayFS выполняет **copy-up**: создаёт представление файла в `upperdir`.

Исходная версия в `lowerdir` не изменяется.

`merged` показывает актуальное объединённое состояние.

### Дополнительный эксперимент

Создайте новый файл:

```bash
echo "created through merged" | \
sudo tee overlay_test/merged/new.txt
```

Посмотрите:

```bash
ls overlay_test/lower
ls overlay_test/upper
```

Где находится `new.txt`?

### Инструменты

`mount`, `umount`, `find`, `ls`, `cat`, `tee`

### Самопроверка

Объясните:

- роль `lowerdir`;
- роль `upperdir`;
- роль `workdir`;
- роль `merged`;
- что означает copy-up;
- почему изменение файла не изменило lower layer.

### Очистка

```bash
sudo umount ~/seminar6/overlay_test/merged
sudo rm -rf ~/seminar6/overlay_test
```

## Задача 9. Посмотрите на файловую систему Docker-контейнера

### Условие

В Linux Docker использует механизмы ядра для изоляции контейнеров. Файловая система контейнера зависит от используемого storage driver.

Прежде чем исследовать OverlayFS Docker, проверьте driver:

```bash
docker info | grep -i "Storage Driver"
```

Если используется:

```text
overlay2
```

продолжайте.

### Запустите контейнер

```bash
docker run -d \
  --name filesystem-demo \
  ubuntu sleep infinity
```

Посмотрите:

```bash
docker inspect filesystem-demo
```

Более точечно:

```bash
docker inspect \
  --format '{{json .GraphDriver.Data}}' \
  filesystem-demo
```

Получите UpperDir:

```bash
docker inspect \
  --format '{{.GraphDriver.Data.UpperDir}}' \
  filesystem-demo
```

Сохраните:

```bash
upper=$(docker inspect \
  --format '{{.GraphDriver.Data.UpperDir}}' \
  filesystem-demo)
```

### Создайте файл в контейнере

```bash
docker exec filesystem-demo \
  sh -c 'echo "Created in container" > /root/demo.txt'
```

Проверьте:

```bash
docker exec filesystem-demo cat /root/demo.txt
```

Теперь на host:

```bash
sudo cat "$upper/root/demo.txt"
```

Сравните.

### Обсудите

Почему файл, созданный внутри container:

```text
/root/demo.txt
```

появился в `UpperDir`?

Почему он не стал частью базового Ubuntu image?

Посмотрите `LowerDir`:

```bash
docker inspect \
  --format '{{.GraphDriver.Data.LowerDir}}' \
  filesystem-demo
```

Обратите внимание: lower layers может быть несколько.

### Инструменты

`docker run`, `docker inspect`, `docker exec`, `docker info`

### Самопроверка

Объясните:

- что такое writable layer контейнера;
- почему изменение контейнера не изменяет image;
- какую связь этот механизм имеет с предыдущей задачей про OverlayFS.

### Очистка

```bash
docker rm -f filesystem-demo
```

## Задача 11. Исследуйте Docker named volume

### Условие

Теперь Docker сам будет управлять местом хранения данных.

Создайте:

```bash
docker volume create seminar6-data
```

Посмотрите:

```bash
docker volume ls
```

Исследуйте:

```bash
docker volume inspect seminar6-data
```

### Первый контейнер

```bash
docker run -d \
  --name volume-demo-1 \
  --mount type=volume,source=seminar6-data,target=/data \
  ubuntu sleep infinity
```

Создайте:

```bash
docker exec volume-demo-1 \
  sh -c 'echo "Persistent data" > /data/file.txt'
```

Проверьте:

```bash
docker exec volume-demo-1 cat /data/file.txt
```

Удалите container:

```bash
docker rm -f volume-demo-1
```

### Второй контейнер

```bash
docker run --rm \
  --mount type=volume,source=seminar6-data,target=/data \
  ubuntu cat /data/file.txt
```

Вы должны увидеть:

```text
Persistent data
```

### Инструменты

`docker volume create`, `docker volume ls`, `docker volume inspect`, `docker volume rm`, `docker run`, `docker exec`

### Самопроверка

Объясните различия:

| Механизм | Где живут данные | После удаления контейнера |
|---|---|---|
| Writable layer | В слое контейнера | исчезают вместе с контейнером |
| Bind mount | В выбранной директории host | сохраняются |
| Named volume | В storage, которым управляет Docker | сохраняются |

### Очистка

```bash
docker volume rm seminar6-data
rm -rf ~/seminar6/host_data
```

## Проверка и сдача работы

### Артефакт

Работа сдаётся одним архивом. По ходу выполнения задач семинара сохраняйте ключевые выводы команд и ответы на вопросы в каталог:

```text
s6-results/
├── task1-links.txt        # задача 1: ls -li, stat, выводы про жёсткую/символьную ссылки
├── task2-mounts.txt       # задача 2: findmnt, mount, df, namei
├── task3-devices.txt      # задача 3: ls -l /dev/null /dev/zero /dev/urandom, stat
├── task4-loop.txt         # задача 4: mkfs.ext4, mount -o loop, losetup, lsblk
├── task5-tmpfs.txt        # задача 5: tmpfs, df, free
├── task6-procfs.txt       # задача 6: /proc/cpuinfo, /proc/meminfo, /proc/self/cmdline
├── task7-bind.txt         # задача 7: bind mount, содержимое до/после
├── task8-overlay.txt      # задача 8: OverlayFS lowerdir/upperdir/workdir/merged
├── task9-docker.txt       # задача 9: файловая система контейнера Docker
├── task10-layer.txt       # задача 10: writable layer vs bind mount
├── task11-volume.txt      # задача 11: Docker named volume
├── answers.txt            # письменные ответы на вопросы «Объясните…», «Почему…»
└── session.txt            # запись терминальной сессии (script -a s6-results/session.txt)
```

### Как подготовить артефакт

```bash
# 1. Создайте каталог результатов и включите запись сессии
mkdir -p s6-results
script -a s6-results/session.txt

# 2. Выполняйте задачи семинара, важные выводы сохраняйте в соответствующие файлы.
#    Пример:
#    ls -li original.txt hard.txt symbolic.txt >> s6-results/task1-links.txt
#    stat original.txt >> s6-results/task1-links.txt

# 3. Ответы на все вопросы самопроверки записывайте в s6-results/answers.txt
#    по мере выполнения задач.

# 4. Завершите запись сессии
exit
```

### Персонализированное задание (защита от списывания)

Часть ответов в `answers.txt` индивидуальна — она зависит от ваших фамилии, имени и от результатов ваших собственных команд (например, номера inode, которые различаются от машины к машине). Просто скопировать файл у соседа не получится.

### Как проверить работу

Из каталога семинара выполните:

```bash
chmod +x check.sh
./check.sh
```

Скрипт проверит состав `s6-results/`, содержимое ключевых файлов и, если всё в порядке, соберёт архив:

```text
s6-results-<Фамилия>-<хеш>.tar.gz
```

Отправьте этот файл своему семинаристу (канал связи уточните на занятии). В теме сообщения укажите: `Семинар 6 Файловые системы — ФИО`.

Вы можете приложить скриншот вывода `./check.sh` как дополнительное доказательство выполнения.
