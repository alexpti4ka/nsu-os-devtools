На этом семинаре вы научитесь превращать исходный код на C в работающую программу и познакомитесь с инструментами, которые делают этот процесс управляемым.

Материал семинара опирается на лекцию по языку C. **Реализовывать алгоритмы на C не требуется**: в репозитории подготовлен готовый проект `seminar3-build-systems`, на котором вы будете упражняться в компиляции и сборке.

Все незавершённые на семинаре задачи необходимо закончить самостоятельно.

> Инструменты, изученные на предыдущих занятиях, перечисляются в разделе **«Инструменты»** только как напоминание. Необходимые параметры команд нужно вспоминать самостоятельно или находить в документации.

## Задача 1. Подготовьте инструменты и проект

### Условие

Убедитесь, что в вашей Linux-среде доступны компилятор и система сборки:

```bash
gcc --version
make --version
```

При необходимости установите пакеты `gcc` и `make` через пакетный менеджер (навыки семинара 1 вам пригодятся).

Склонируйте или обновите репозиторий курса и перейдите в каталог проекта:

```bash
cd seminar3-build-systems
```

Изучите его структуру:

```text
seminar3-build-systems/
├── src/        реализации функций
├── include/    публичные заголовочные файлы
├── tests/      небольшие тестовые программы
├── bench/      эксперименты с оптимизацией
├── variants/   взаимозаменяемые реализации политики
├── stages/     пример для изучения этапов компиляции
└── data/       входные текстовые файлы
```

Прочитайте заголовочные файлы в `include/` и постарайтесь понять, какие функции предоставляет каждая часть проекта. Заглядывать в реализацию `.c`-файлов не обязательно: на этом семинаре важно не **что** делает код, а **как** он превращается в программу.

### Инструменты

`gcc`, `make`, `apt`, `find`, `tree`

Из предыдущих семинаров: `ls`, `cat`, `cd`, `less`

### Самопроверка

Команды `gcc --version` и `make --version` работают, и вы можете ответить:

* чем заголовочный файл `.h` отличается от файла реализации `.c`;
* зачем объявления функций вынесены в `include/`.

## Задача 2. Соберите программу одним вызовом компилятора

### Условие

Соберите основной проект `textstat` одной командой: компилятору нужно передать все `.c`-файлы из `src/` и путь для поиска заголовков.

Имя итогового исполняемого файла выберите сами (например, `textstat`).

Запустите программу на файлах из `data/`:

```bash
./textstat data/small.txt
./textstat data/large.txt
```

Изучите, как выглядит вывод. Затем попробуйте запустить программу без аргументов и с несуществующим файлом и посмотрите на код возврата:

```bash
echo $?
```

### Инструменты

`gcc`, `echo`, `man gcc`

### Самопроверка

Программа корректно обрабатывает оба файла из `data/`, сообщает об ошибке при отсутствии файла и возвращает ненулевой код выхода.

## Задача 3. Разберитесь с этапами компиляции

### Условие

Одна команда `gcc` скрывает несколько отдельных этапов. Используя файл из каталога `stages/`, воспроизведите их по отдельности.

Постройте и изучите результат работы препроцессора:

```bash
gcc -E stages/stages.c -I stages/include -o /tmp/stages.i
```

Найдите в полученном файле:

* след подключённого заголовка `config.h`;
* во что развернулся макрос `SQUARE`;
* подставленное значение константы из `config.h`.

Затем получите код ассемблера (`gcc -S`), объектный файл (`gcc -c`) и, наконец, слинкуйте его в исполняемый файл. Запустите результат.

Сохраните промежуточные файлы в отдельный каталог, чтобы не засорять проект.

### Инструменты

`gcc -E`, `gcc -S`, `gcc -c`, `gcc`, `less`, `grep`

### Самопроверка

Вы можете перечислить этапы компиляции по порядку и объяснить своими словами:

* чем объектный файл отличается от исполняемого;
* почему в объектном файле ещё нет готовой программы;
* что делает флаг `-I` и почему он нужен в этом проекте.

## Задача 4. Соберите проект по частям

### Условие

Повторите сборку проекта, но теперь явно, по шагам:

1. скомпилируйте каждый `.c`-файл из `src/` в отдельный объектный файл;
2. слинкуйте полученные объектные файлы в исполняемый файл `textstat`;
3. убедитесь, что программа работает так же, как в задаче 2.

Затем используйте `variants/`: там лежат три взаимозаменяемые реализации политики подсчёта оценки (`policy-a.c`, `policy-b.c`, `policy-c.c`). Ваша сборка должна использовать только **одну** из них.

Соберите три версии программы, каждая со своей политикой, и сравните их вывод на одном и том же файле из `data/`.

### Инструменты

`gcc -c`, `gcc`, `mv`, `diff`

### Самопроверка

Вывод трёх версий программы различается, при этом остальной код проекта не менялся.

## Задача 5. Автоматизируйте сборку с помощью Makefile

### Условие

Ручная сборка по шагам быстро надоедает. Опишите её в `Makefile` в корне проекта.

В Makefile должны быть цели:

* сборка исполняемого файла `textstat` из объектных файлов;
* создание каждого объектного файла;
* сборка и запуск тестов из `tests/`;
* очистка проекта от результатов сборки.

Убедитесь, что:

* первая сборка компилирует всё;
* повторный вызов ничего не пересобирает;
* после изменения одного `.c`-файла пересобирается только он и перелинковывается программа;
* очистка удаляет все сгенерированные файлы, но не исходники.

### Инструменты

`make`, `make clean`, `man make`, `vim`

Из предыдущих семинаров: `touch`, `ls`, `rm`

### Самопроверка

Последовательность:

```bash
make
make
touch src/tokenizer.c
make
make clean
```

работает ровно так, как описано в условии.

Попробуйте объяснить, как `make` понимает, что файл нужно пересобрать, и зачем в Makefile нужны переменные и шаблоны правил.

## Задача 6. Измерьте влияние оптимизаций

### Условие

В каталоге `bench/` лежит небольшая вычислительная программа.

Соберите её с разными уровнями оптимизации и измерьте время работы каждого варианта:

```bash
gcc -O0 bench/benchmark.c -o /tmp/bench-o0
gcc -O2 bench/benchmark.c -o /tmp/bench-o2
gcc -O3 bench/benchmark.c -o /tmp/bench-o3
```

Для измерения времени используйте утилиту `time`.

Запустите каждый вариант на одинаковом количестве итераций (аргумент командной строки программы) и сравните результаты: время работы и вывод программы.

### Инструменты

`gcc -O`, `time`, `man gcc`

### Самопроверка

Время работы при `-O2`/`-O3` заметно меньше, чем при `-O0`, при этом вывод программы одинаков.

Убедитесь, что можете объяснить:

* на каком этапе компиляции работает оптимизация;
* почему уровень оптимизации не меняет результат вычислений;
* зачем разработчику сравнивать разные уровни оптимизации, а не всегда использовать максимальный.

## Задача 7. Приведите проект в порядок

### Условие

После выполнения задач в каталоге проекта накопились промежуточные файлы: объектные файлы, исполняемые файлы, результаты препроцессора.

Сначала убедитесь, что можете отличить исходники от сгенерированных файлов. Для этого:

* посмотрите содержимое каталога проекта и перечислите, какие файлы появились в процессе работы;
* проверьте, что `make clean` удаляет всё созданное вами;
* убедитесь, что после очистки проект собирается заново одной командой и программа работает.

Важно, чтобы после очистки в проекте остались только исходные файлы — ровно те, с которых вы начинали.

### Инструменты

`make clean`, `make`, `find`, `ls`

Из предыдущих семинаров: `ls`, `find`, `rm`

### Самопроверка

После `make clean` в каталоге проекта не остаётся ни одного сгенерированного файла, а повторный `make` снова создаёт работающий `textstat`.

Попробуйте объяснить, почему сгенерированные файлы не принято хранить вместе с исходниками и зачем нужна цель `clean`.

Попробуйте объяснить, на каком этапе сборки определяется, какая реализация `policy` попадёт в программу, и почему заголовок `policy.h` один и тот же для всех вариантов.

Попробуйте объяснить, почему вызов компилятора «в один шаг» становится неудобным, когда `.c`-файлов в проекте становится много.
