## Задача 8. Соберите динамическую библиотеку

### Условие

Теперь соберите те же модули в динамическую (shared) библиотеку `libtextstat.so`.

> Задача рассчитана на Linux-среду курса: здесь используются ELF-файлы, флаг `-shared` и утилита `ldd`.

Объектные файлы для shared-библиотеки компилируются с позиционно-независимым кодом: библиотека должна быть пригодна для загрузки по разным адресам памяти.

```bash
mkdir -p /tmp/s3
gcc -fPIC -c -I include src/tokenizer.c -o /tmp/s3/tokenizer.o
gcc -fPIC -c -I include src/stats.c     -o /tmp/s3/stats.o
gcc -fPIC -c -I include src/formatter.c -o /tmp/s3/formatter.o
gcc -fPIC -c -I include src/policy.c    -o /tmp/s3/policy.o
gcc -shared -o /tmp/s3/libtextstat.so /tmp/s3/tokenizer.o /tmp/s3/stats.o /tmp/s3/formatter.o /tmp/s3/policy.o
```

Соберите `textstat-shared`, связанный с этой библиотекой, и посмотрите его runtime-зависимости:

```bash
gcc -c -I include src/main.c -o /tmp/s3/main.o
gcc /tmp/s3/main.o -L/tmp/s3 -ltextstat -o textstat-shared
ldd ./textstat-shared
./textstat-shared data/small.txt
```

Затем временно уберите `libtextstat.so` так, чтобы dynamic loader перестал её находить, и снова попробуйте запустить программу:

```bash
mv /tmp/s3/libtextstat.so /tmp/s3/libtextstat.so.bak
./textstat-shared data/small.txt
# error while loading shared libraries: libtextstat.so: cannot open shared object file
mv /tmp/s3/libtextstat.so.bak /tmp/s3/libtextstat.so
LD_LIBRARY_PATH=/tmp/s3 ./textstat-shared data/small.txt
```

Верните библиотеку на место и настройте окружение процесса так, чтобы программа снова её находила.

### Инструменты

`gcc -fPIC`, `gcc -shared`, `ldd`, `mv`, `env`, `export`, `LD_LIBRARY_PATH`, `man`

### Самопроверка

`ldd` показывает зависимость `textstat-shared` от `libtextstat.so`, а при убранной библиотеке программа не запускается и dynamic loader сообщает об ошибке.

Вы можете объяснить:

* почему для shared-библиотеки нужны объектные файлы, собранные с `-fPIC`;
* почему наличие `.so` важно не только при сборке, но и при запуске программы;
* что делает `LD_LIBRARY_PATH`.

* динамическим executable;
* динамической библиотекой.

Попробуйте запустить полученные файлы, а затем подменить `.so` одной реализации на `.so` другой при неизменном executable.

> `textstat-static` означает, что `libtextstat` встроена в executable. Это **не** гарантирует, что файл запустится на любой Linux-машине: он всё ещё может зависеть от системных библиотек, например glibc.

### Инструменты

`gcc`, `ar`, `file`, `stat`, `ldd`, `cp`, `mv`, `LD_LIBRARY_PATH`, `man`

### Самопроверка

Вы можете объяснить:

* почему встроенная `libtextstat` проще ровно в отношении этой зависимости;
* почему динамической программе нужна совместимая `.so`;
* как одна и та же программа меняет поведение при подмене реализации библиотеки с тем же интерфейсом.

## Задача 10. Опишите сборку в Makefile

### Условие

К этому моменту для сборки проекта приходится вручную повторять большое количество команд компиляции, архивирования и линковки. Опишите их в `Makefile` в корне проекта.

На первом этапе Makefile должен быть намеренно явным: отдельное правило для каждого объектного файла.

```text
main.o
tokenizer.o
stats.o
formatter.o
policy.o
clean
```

Разберитесь в структуре правила Make:

```make
target: prerequisites
```

Добавьте корректное описание целей, которые не представляют реальные файлы.

Убедитесь, что:

* первая сборка компилирует всё;
* повторный вызов ничего не пересобирает;
* после изменения одного `.c`-файла пересобирается только он и перелинковывается программа;
* очистка удаляет все сгенерированные файлы, но не исходники.

### Инструменты

### Самопроверка

```bash
make
make clean
```

работает ровно так, как описано в условии.

Вы можете объяснить, как `make` понимает, что файл нужно пересобрать, и зачем нужны `.PHONY`-цели и переменные (об этом — следующие задачи).

## Задача 13. Уберите дублирование из Makefile

### Условие

Текущий Makefile содержит много почти одинаковых правил компиляции.

Список исходных файлов должен остаться **явным**: не подключайте автоматически каждый `.c`-файл, случайно появившийся в `src/`.

На основе явного списка исходников:

* сформируйте список объектных файлов средствами Make;
* замените повторяющиеся правила одним шаблонным правилом;
* используйте автоматические переменные вместо повторения имён цели и предпосылок;
* вынесите компилятор и группы флагов в переменные Make.

Используйте стандартные имена переменных там, где это уместно:

```text
CC
CPPFLAGS
CFLAGS
LDFLAGS
LDLIBS
```

Исследуйте функцию `wildcard`. Подумайте, почему автоматическое включение всех `.c`-файлов из каталога — не всегда хорошая политика состава сборки.

### Инструменты

`make`, `gcc`, `clang`, `vim`, `grep`, `man`

### Самопроверка

Добавление ещё одного файла в **явный список** исходников не требует копирования отдельного правила компиляции.

Makefile содержит существенно меньше повторяющегося текста, а состав проекта остаётся явно контролируемым.

## Задача 15. Добавьте тесты в сборку

### Условие

В `tests/` находятся три уже написанных теста:

```text
test_tokenizer.c
test_stats.c
test_policy.c
```

Каждый тест возвращает нулевой код выхода при успехе и ненулевой при ошибке. В конце каждый тест выполняется с искусственной задержкой в 2 секунды — так удобнее сравнивать последовательный и параллельный запуск.

Добавьте сборку тестов в Makefile.

Сначала создайте цель `test`, которая последовательно собирает и запускает все тестовые программы, и измерьте полное время:

```bash
time make test
```

После этого перестройте граф целей так, чтобы запуск каждого теста представлял отдельную независимую цель, а общая цель `test` зависела от них. Запустите тесты параллельно средствами Make и сравните время с последовательным запуском:

```bash
time make -j3 test
```

Исследуйте, как ограничивается число одновременно выполняемых jobs.

### Инструменты

`make`, `make -j`, `time`, `gcc`, `clang`, `man`

### Самопроверка

Все три теста успешно завершаются и при последовательном, и при параллельном запуске. Два теста печатают отчёт об успехе, третий только возвращает нулевой код — ориентируйтесь на код возврата.

Параллельный запуск занимает заметно меньше времени.

Вы можете объяснить, почему Make может безопасно выполнять параллельно только независимые ветви графа.

## Задача 16. Соберите проект полностью одной системой сборки

### Условие

Приведите Makefile к итоговому состоянию. Он должен поддерживать:

* обычную сборку;
* очистку результатов;
* debug- и release-конфигурации;
* GCC и Clang;
* статическую и динамическую библиотеку;
* корректные зависимости от заголовков;
* инкрементальную пересборку;
* сборку и запуск тестов;
* параллельный запуск независимых тестов.

Организуйте результаты сборки так, чтобы исходники не смешивались с `.o`, `.d`-файлами, библиотеками и исполняемыми файлами. Необязательно в точности повторять структуру, но итог может выглядеть примерно так:

```text
seminar3-build-systems/
├── src/
├── include/
├── tests/
├── build/
├── lib/
├── bin/
└── Makefile
```

Убедитесь, что можете отличить исходники от сгенерированных файлов:

* посмотрите содержимое каталога проекта и перечислите, какие файлы появились в процессе работы;
* проверьте, что `make clean` удаляет всё созданное;
* убедитесь, что после очистки проект собирается заново одной командой и программа работает.

Важно, чтобы после очистки в проекте остались только исходные файлы — ровно те, с которых вы начинали.

### Инструменты

`make`, `gcc`, `clang`, `ar`, `file`, `stat`, `find`, `tree`, `grep`, `env`, `man`

### Самопроверка

Измените один `.c`-файл, затем один `.h`-файл, и убедитесь, что в каждом случае пересобирается только необходимая часть графа.

Вы можете объяснить, почему сгенерированные файлы не принято хранить вместе с исходниками, и почему вызов компилятора «в один шаг» становится неудобным, когда `.c`-файлов в проекте становится много.
