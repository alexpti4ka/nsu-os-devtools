## Задача 5. Разделите обычный вывод и сообщения об ошибках

### Условие

`seminar2-generator` имитирует работающую программу. Во время работы он:
- создаёт новые текстовые файлы в `incoming`;
- записывает структурированные события в стандартный вывод `stdout`;
- записывает диагностические сообщения и ошибки в стандартный поток ошибок `stderr`.

Сначала изучите справку программы и запустите генератор на небольшом количестве событий без перенаправлений. Посмотрите, какие сообщения появляются в терминале.

На прошлом семинаре вы использовали `>` и `>>`. Уточните модель стандартных потоков:

```
stdin  = 0
stdout = 1
stderr = 2
```

Проверьте экспериментально, что `>` является сокращённой записью для перенаправления `stdout`.

Запустите генератор так, чтобы:

- `stdout` записывался в `logs/events.log`;
- `stderr` записывался отдельно в `logs/generator.err`.

Затем запустите генератор ещё раз и **добавьте** новые данные в оба существующих файла, не уничтожая старые.

После этого запустите генератор на достаточно большом количестве событий, чтобы `events.log` содержал несколько тысяч строк.

### Инструменты

`>`, `>>`, `1>`, `1>>`, `2>`, `2>>`, `cat`, `ls`, `man`

### Самопроверка

В директории `logs` должны существовать два независимых файла:

```
events.log
generator.err
```

`events.log` должен содержать структурированные записи вида:

```
timestamp|level|source|file|status
```

`generator.err` должен содержать диагностические сообщения генератора.

Убедитесь, что понимаете, почему перенаправление только `stdout` не скрывает сообщения из `stderr`.

## Задача 8. Преобразуйте содержимое файлов с помощью `sed`

### Условие

В `config/service.conf` находится исходная конфигурация файлового конвейера.

Не изменяя исходный файл, создайте:

```
config/service-active.conf
```

В новой конфигурации:

- режим `dry-run` должен быть заменён на `active`;
- уровень журналирования `debug` должен быть заменён на `info`;
- пути к входным и обработанным данным должны указывать на директории внутри `~/seminar2/control-center`.

Сначала выполните каждое преобразование так, чтобы результат выводился только в терминал. После проверки сохраните итоговый результат в новый файл.

Теперь выберите один из сгенерированных файлов в `incoming`.

Создайте его обработанную версию в `processed`:
- замените заданное слово или значение во всех строках;
- удалите или выведите только строки, соответствующие заданному шаблону;
- исходный файл в `incoming` оставьте неизменным.

С помощью `sed` также сформируйте:

```
reports/errors.log
```

содержащий только события уровня `ERROR` из `events.log`.

### Инструменты

`sed`, `cat`, `grep`, `>`, `cp`, `man`

### Самопроверка

Исходные файлы в `incoming` и `config/service.conf` не должны измениться.

`config/service-active.conf` должна содержать только требуемые изменения.

Количество строк в `reports/errors.log` должно совпадать с количеством событий `ERROR`, полученным в предыдущей задаче.

1. Дождитесь появления нового файла в `incoming`.
2. Просмотрите его через MC.
3. Преобразуйте его содержимое изученными текстовыми утилитами и сохраните результат в `processed`.
4. Убедитесь через MC, что новый файл появился.
5. Посмотрите в окне мониторинга соответствующие события и диагностику.
6. Скопируйте итоговый отчёт и рабочую конфигурацию в `backup`.

### Инструменты

`mc`, `tmux`, `sed`, `grep`, `cat`, `cp`, `mv`, `rm`, `mkdir`, `tail`, `|`, `>`, `man`

### Самопроверка

После выполнения задачи в tmux должны одновременно быть доступны:

- живой генератор;
- наблюдение за журналом;
- shell для анализа;
- конфигурация в Vim;
- файловый интерфейс MC.

В `processed` должен находиться хотя бы один преобразованный файл, а в `backup` — копии отчёта и рабочей конфигурации.

Отсоединитесь от tmux и снова подключитесь. Рабочий центр должен сохраниться.

Попробуйте определить, для каких действий удобнее:
- обычные команды shell;
- конвейеры;
- Vim;
- Midnight Commander;
- tmux.
