# Лабораторная работа. Сборка и запуск многоконтейнерного приложения на C

**Тема:** GCC, Make, статические библиотеки, Dockerfile, Docker Compose.

## 1. Цель работы

Организовать сборку многокомпонентного проекта на C и запуск его частей в Docker-контейнерах.

Программы на C уже написаны. **Изменять файлы `.c` и `.h` не нужно.** В корне проекта также находится **готовый `Makefile`**, который управляет сборкой всех компонентов. Необходимо написать только Makefile отдельных компонентов и конфигурацию Docker.

## 2. Описание системы

Проект включает три приложения:

- **backend** — HTTP-сервер. В ответ на `GET /` возвращает сообщение с именем сервера.
- **balancer** — принимает HTTP-запросы и по очереди направляет их двум backend-серверам (Round Robin).
- **loadgen** — отправляет запросы балансировщику, измеряет время ответа и записывает результаты в CSV.

В итоговой системе должны работать четыре контейнера: два экземпляра `backend`, один `balancer`, один `loadgen`.

```text
                       Компьютер
                  http://localhost:8080
                           |
                           v
                       balancer
                       порт 8080
                       /       \
                      v         v
               backend-1     backend-2
                порт 9000     порт 9000

                       loadgen
                          |
                          v
                   balancer:8080
                          |
                  результаты в CSV
```

## 3. Структура проекта и зависимости

В выданном архиве находится следующая структура:

```text
c-lab-multiservice/
├── Makefile                 # Готовый, изменять не нужно
├── include/
│   ├── net.h
│   ├── http.h
│   └── utils.h
├── lib/
│   ├── net.c
│   ├── http.c
│   └── utils.c
├── apps/
│   ├── backend/
│   │   ├── main.c
│   │   ├── handler.c
│   │   └── handler.h
│   ├── balancer/
│   │   ├── main.c
│   │   ├── router.c
│   │   └── router.h
│   └── loadgen/
│       ├── main.c
│       ├── stats.c
│       └── stats.h
└── README.md
```

Общие функции объявлены в `include/` и реализованы в `lib/`. Из `net.c`, `http.c` и `utils.c` необходимо собрать **статическую библиотеку** `build/lib/libcommon.a`.

Все три приложения используют эту библиотеку:

```text
     lib/net.c  lib/http.c  lib/utils.c
                  |
                  v
       build/lib/libcommon.a
            /     |     \
           v      v      v
       backend  balancer  loadgen
```

Исходники приложений распределены следующим образом:

| Приложение | Собственные исходники | Результат сборки |
|---|---|---|
| backend | `main.c`, `handler.c` | `apps/backend/backend` |
| balancer | `main.c`, `router.c` | `apps/balancer/balancer` |
| loadgen | `main.c`, `stats.c` | `apps/loadgen/loadgen` |

**Порядок сборки:** сначала общая библиотека, затем приложения. Корневой `Makefile` уже задаёт этот порядок.

## 4. Какие файлы необходимо написать

Всего необходимо создать **9 файлов**:

| Файл | Назначение |
|---|---|
| `lib/Makefile` | Сборка статической библиотеки `libcommon.a` |
| `apps/backend/Makefile` | Сборка `backend` с общей библиотекой |
| `apps/balancer/Makefile` | Сборка `balancer` с общей библиотекой |
| `apps/loadgen/Makefile` | Сборка `loadgen` с общей библиотекой |
| `apps/backend/Dockerfile` | Образ backend |
| `apps/balancer/Dockerfile` | Образ balancer |
| `apps/loadgen/Dockerfile` | Образ loadgen |
| `compose.yaml` | Запуск и настройка четырёх контейнеров |
| `.dockerignore` | Исключение ненужных файлов из контекста сборки |

**Корневой `Makefile` писать или изменять не нужно.**

### 4.1. Требования к дочерним Makefile

- `lib/Makefile` должен собирать общую библиотеку из трёх исходных файлов и размещать её в `build/lib/libcommon.a` относительно корня проекта.
- Каждый Makefile приложения должен собирать собственный исполняемый файл из двух `.c` и связывать его с общей библиотекой.
- Сборка должна находить заголовочные файлы из корневого каталога `include/`.
- Все четыре дочерних Makefile должны поддерживать цели `all` и `clean`.
- После запуска `make` из корня должны создаваться библиотека и три исполняемых файла. После `make clean` результаты сборки должны удаляться.

**Переменные окружения в Makefile:**

- Используйте переменную `CC` для выбора компилятора и `CFLAGS` для параметров компиляции. Их значения должны допускать переопределение через окружение при запуске `make`.
- Если эти переменные не заданы извне, сборка должна работать со значениями по умолчанию.
- Для повторяющихся путей можно использовать простые переменные Makefile, например `INCLUDE_DIR` и `LIB_DIR`.

Достаточно обычных переменных и простых правил с явно перечисленными файлами. **Не требуются** шаблонные правила, автоматические зависимости от заголовков, сложные функции Make или отдельные каталоги объектных файлов для каждого приложения.

### 4.2. Требования к Dockerfile

Для каждого приложения создайте отдельный Dockerfile с **двухэтапной сборкой**:

1. В первом этапе должна выполняться сборка общей библиотеки и соответствующего приложения.
2. Во втором этапе должен находиться только готовый исполняемый файл и необходимые компоненты среды исполнения, без компилятора и инструментов сборки.

Можно использовать образы `gcc:13-bookworm` и `debian:bookworm-slim`.

Общая библиотека и заголовочные файлы находятся вне каталогов отдельных приложений. Это необходимо учесть при выборе контекста сборки Docker.

### 4.3. Требования к Docker Compose

Опишите сервисы со следующими именами: `backend-1`, `backend-2`, `balancer`, `loadgen`. Два backend должны использовать **один и тот же Dockerfile**, но работать в отдельных контейнерах.

**Порты:**

| Сервис | Порт внутри контейнера | Доступ с компьютера |
|---|---|---|
| `backend-1` | `9000` | Не публиковать |
| `backend-2` | `9000` | Не публиковать |
| `balancer` | `8080` | Опубликовать на порту `8080` |
| `loadgen` | Входящий порт не нужен | Не публиковать |

Внутри сети Docker Compose нужно использовать имена сервисов для обращения к другим контейнерам. Для `loadgen` настройте сохранение CSV в локальном каталоге `results/`. Предусмотрите порядок запуска: сначала backend, затем balancer, затем loadgen.

**Переменные окружения приложений:**

| Сервис | Переменная | Значение |
|---|---|---|
| `backend-1` | `PORT` | `9000` |
| `backend-1` | `SERVER_NAME` | `backend-1` |
| `backend-2` | `PORT` | `9000` |
| `backend-2` | `SERVER_NAME` | `backend-2` |
| `balancer` | `PORT` | `8080` |
| `balancer` | `BACKENDS` | `backend-1:9000,backend-2:9000` |
| `loadgen` | `TARGET_HOST` | `balancer` |
| `loadgen` | `TARGET_PORT` | `8080` |
| `loadgen` | `REQUEST_COUNT` | `1000` |
| `loadgen` | `OUTPUT_FILE` | `/results/result.csv` |

Каталог `/results` контейнера `loadgen` должен соответствовать каталогу `results/` в корне проекта на компьютере.

## 5. Проверка работоспособности

Все проверки выполняются из корня проекта.

### 5.1. Локальная сборка

Выполните `make` и убедитесь, что созданы файлы:

```text
build/lib/libcommon.a
apps/backend/backend
apps/balancer/balancer
apps/loadgen/loadgen
```

Проверьте, что `make clean` удаляет результаты сборки, а последующий `make` снова собирает проект.

Отдельно проверьте, что при изменении значений `CC` и `CFLAGS`, передаваемых через окружение, дочерние Makefile используют их при новой сборке.

### 5.2. Запуск контейнеров

Соберите образы и запустите систему с помощью Docker Compose.

Проверьте состояние контейнеров и журналы `loadgen`. После завершения нагрузки `loadgen` должен завершиться успешно, а другие три контейнера — продолжить работу.

Ожидаемое сообщение в журнале генератора:

```text
Requests: 1000, successful: 1000, failed: 0
```

### 5.3. Работа балансировщика

Выполните несколько HTTP-запросов:

```bash
curl http://localhost:8080/
curl http://localhost:8080/
curl http://localhost:8080/
```

Ответы должны чередоваться между:

```text
Hello from backend-1
Hello from backend-2
```

Первый ответ может принадлежать любому backend, если балансировщик уже обслуживал запросы.

### 5.4. Результаты нагрузки

Проверьте файл `results/result.csv`. В нём должно быть **1001 строка**: заголовок и 1000 результатов запросов. Ожидаемые столбцы:

```csv
request_id,backend,latency_ms,status
```

При отсутствии параллельных запросов ожидается примерно поровну, а для последовательного генератора — по 500 ответов от каждого backend.

### 5.5. Изменение конфигурации

Измените `REQUEST_COUNT` в конфигурации Compose с `1000` на `100` и повторно запустите `loadgen` без пересборки образов. В результирующем CSV должна быть **101 строка** с учётом заголовка.

## 6. Что показать преподавателю

1. Четыре созданных дочерних Makefile и результаты локальной сборки.
2. Использование переменных `CC` и `CFLAGS`, включая переопределение из окружения.
3. Три двухэтапных Dockerfile и файл `compose.yaml`.
4. Работающий балансировщик, чередующий ответы двух backend.
5. CSV-файл с результатами нагрузки и изменение количества запросов без пересборки образов.

**Критерий выполнения:** проект собирается готовым корневым Makefile, четыре контейнера запускаются, приложения взаимодействуют через сеть Docker Compose, а результаты `loadgen` сохраняются на компьютере.

## 7. Сдача работы

### Артефакт

Работа сдаётся одним архивом. Подготовьте каталог результатов:

```text
lab1-results/
├── build/               # результаты `make` (libcommon.a, backend, balancer, loadgen)
├── results/             # result.csv от loadgen
├── Dockerfile*          # три Dockerfile (backend, balancer, loadgen)
├── compose.yaml
├── check-output.txt     # вывод ./check.sh
└── answers.txt          # ответы на персонализированные вопросы
```

### Как подготовить артефакт

```bash
# 1. Выполните все пункты разделов 3–6 README (напишите Makefile, Dockerfile, compose.yaml).
# 2. Соберите проект: make
# 3. Запустите контейнеры: docker compose up
# 4. Сохраните результаты:
mkdir -p lab1-results/build lab1-results/results
cp build/lib/libcommon.a apps/backend/backend apps/balancer/balancer apps/loadgen/loadgen lab1-results/build/
cp apps/backend/Dockerfile apps/balancer/Dockerfile apps/loadgen/Dockerfile compose.yaml lab1-results/
cp results/result.csv lab1-results/results/ 2>/dev/null || true
```

2. Какие переменные окружения (`CC`, `CFLAGS`) вы переопределяли при сборке, и как это повлияло на результат?

4. Опишите своими словами, как балансировщик распределяет запросы между двумя backend.

Из каталога `c-lab-multiservice/` выполните:

```bash

```

Скрипт проверит, что исходники не изменены, что проект собирается корневым `Makefile`, и соберёт именной архив:

```text
lab1-launcher-<Фамилия>-<хеш>.tar.gz
```

Отправьте архив своему семинаристу. В теме сообщения укажите: `lab1-launcher — ФИО`.

- неизменность исходных файлов `.c` и `.h` (по SHA256);
- успешную локальную сборку (`make` + `make clean` + `make`);
- использование переменных `CC` / `CFLAGS` из окружения;
- наличие четырёх контейнеров в `compose.yaml` (`backend-1`, `backend-2`, `balancer`, `loadgen`);
- наличие `results/result.csv` с нужным количеством строк;
- персональные ответы в `answers.txt`.
