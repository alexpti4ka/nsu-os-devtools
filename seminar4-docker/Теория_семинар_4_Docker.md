# Семинар 4. Docker — теоретический материал

Теоретический материал к семинару «Docker: изоляция, образы, контейнеры,
тома, Compose, ресурсы». Он помогает ответить на вопрос, что такое Docker,
чем контейнер отличается от виртуальной машины, как устроены образы,
контейнеры и хранение данных, и зачем нужны Compose и ограничения
ресурсов.

Как пользоваться материалом: разделы идут в порядке, который совпадает с
порядком заданий семинара — прочитайте нужный раздел перед тем, как
браться за соответствующее задание, и вернитесь к нему на самопроверке.

---

## 0. Главная мысль семинара в одном абзаце

> **Контейнер — это процесс(ы) с перехваченными системными вызовами и
> изолированной корневой файловой системой, а не виртуальная машина.**
> Данные, записанные внутрь контейнера, живут, пока живёт контейнер;
> долгоживущие данные хранят в volumes/bind-mounts.

Четыре термина, которые нужно различать с первого минуты:

```text
image (образ)         → неизменяемый «рецепт» файловой системы + метаданные
container (контейнер) → запущенный экземпляр образа (процессы + изменяемая ФС)
Dockerfile            → рецепт, из которого собирается образ
Docker volume         → хранение данных вне контейнера
```

---

## 1. Что такое Docker (задача 1)

**Docker — это платформа для разработки, доставки и запуска приложений в
контейнерах.** Три слоя, которые важно различать:

| Слой | Что это | Пример |
|---|---|---|
| **Docker Engine (daemon)** | сервис на хосте, который принимает команды CLI, управляет образами/контейнерами/сетями/томами | `dockerd`, `systemctl status docker` |
| **Docker CLI** | клиент, который говорит с daemon по REST API (сокет `/var/run/docker.sock`) | `docker`, `docker build`, `docker run` |
| **Docker Compose** | инструмент для описания и запуска **множества** контейнеров из одного YAML-файла | `docker compose up` |

Container Runtime — то, что реально создаёт контейнеры (`containerd`,
`runc`); Docker Engine — надстройка, которая им управляет и даёт удобный
интерфейс.

Docker решает конкретную боль: программа, которая у вас работает,
должна так же работать у коллеги, в CI и в проде. Он даёт
**воспроизводимое окружение**: та же файловая система, те же пакеты, та же
версия библиотек — потому что запускается не «чистая машина», а упакованный
образ.

Что Docker **не** делает: не заменяет ядро ОС, не компилирует ваш код за
вас, не решает оркестрацию нескольких хостов (это Kubernetes — другая
ступень).

## 2. Docker vs виртуальная машина (задача 2)

Это центральный вопрос семинара. Ключевая разница — **что изолируется и за
счёт чего**.

| Критерий | Виртуальная машина (VM) | Docker-контейнер |
|---|---|---|
| Что запускаем | гостевая ОС целиком (ядро + система) | прикладной процесс(ы) |
| Ядро | **своё** (гостевое, гипервизор эмулирует его) | **общее с хостом** (разделяемое ядро ОС) |
| Механизм изоляции | аппаратная виртуализация: гипервизор (KVM/VMware/Hyper-V), CPU-режимы ring 0/3, вложенная пагинация | механизмы ядра Linux: **namespaces** (изоляция) + **cgroups** (лимиты) + capabilities |
| Что изолируется | целиком: ядро, процессы, память, сеть, ФС, устройства | процессы, память, сеть, ФС, PID, hostname, user-ids |
| Файловая система | гостевая ФС поверх образа диска | слои (overlay FS) поверх read-only образов |
| Запуск | десятки секунд–минуты (boot гостевой ОС) | миллисекунды–секунды (запуск процесса) |
| Плотность на хосте | десятки гостей (каждый ест память под своё ядро) | сотни–тысячи контейнеров |
| Размер дистрибутива | hundreds MB–GB (гостевая ОС) | десятки MB (только нужные файлы) |
| Порог входа | нужен гипервизор, ресурсы, лицензии | достаточно Docker Engine |
| Слабость | тяжёлый, медленный, дублирует ядро для каждой гостевой системы | **слабая изоляция** (общее ядро — и общие уязвимости ядра), ограничен Linux-семантикой |

Как это выглядит «снизу»:

```text
VM:     [Приложение] → [Гостевое ЯДРО] → [Гипервизор] → [Аппаратура/Хост]
Docker: [Приложение] → syscall        → [Ядро хоста (общее)] → [Аппаратура]
```

### Как именно изолирует Linux

- **namespaces** — «своё имя» для ресурсов, невидимое снаружи:
  - `pid` — свои номера процессов (в контейнере `ps` покажет `PID 1`);
  - `mnt` (mount) — своя корневая ФС и набор точек монтирования;
  - `net` — свой сетевой стек, свои IP;
  - `uts` — своё имя хоста;
  - `ipc` — своя межпроцессная коммуникация;
  - `user` — свои UID/GID.
- **cgroups v2** — учёт и **лимиты** CPU, памяти, I/O, числа процессов.
- **capabilities** — минимальный набор прав вместо `root`: контейнеру не
  дают лишние capabilities, он не может, например, загрузить модуль ядра.
- **seccomp / AppArmor / SELinux** — фильтрация системных вызовов.

### Что из этого следует на практике

- Контейнер **видит только «свои» процессы** — «машина» не выглядит
  отдельной ОС.
- Пакеты, установленные внутри контейнера, **не попадают на хост**: это
  другой корень ФС (overlay поверх read-only слоя образа).
- Контейнер не может безопасно запускать код, который должен быть
  изолирован «по-настоящему» от хоста (недоверенный код, разные ОС,
  kernel-level атаки) — для этого нужна ВМ.

**Коротко:**
«Контейнер — не отдельная виртуальная машина: у него нет своего ядра;
это изолированный процесс(ы) с общим ядром хоста, отдельной ФС и
отдельным сетевым и PID-пространством».

## 3. Архитектура: из Dockerfile в контейнер

```text
Dockerfile ──docker build──▶ image (слои) ──docker run──▶ container
              (рецепт)      (шаблон)                    (запущенный экземпляр)
```

- **Dockerfile** — текстовый рецепт: последовательность инструкций
  (`FROM`, `WORKDIR`, `COPY`, `RUN`, `CMD`).
- **image** — результат сборки: набор **слоёв** (layers) + метаданные
  (CMD, ENV, ENTRYPOINT, тома, порты). Образ **неизменяем** и **не
  содержит данных** — это только шаблон.
- **container** — запущенный экземпляр образа: тонкий «слой записи»
  (copy-on-write) поверх слоёв образа + свои процессы, сеть, монтирования.

Один образ → сколько угодно контейнеров. Изменения внутри работающего
контейнера **не попадают** в образ (в отличие от ВМ, где можно «закоммитить
состояние»).

## 4. Жизненный цикл контейнера (задачи 3 и 5)

```text
docker run ──▶ created ──▶ running ──stop──▶ exited ──start──▶ running
                              │                              │
                              └──────── restart ─────────────┘
                                    docker rm ──▶ удалён
                                        (данные исчезли)
```

- `docker run` — это ярлык из трёх действий: **create + start + подключить
  вывод**.
- `docker ps` — только **запущенные**; `docker ps -a` — все, включая
  остановленные.
- `docker exec -it ИМЯ bash` — выполнить команду **внутри уже работающего**
  контейнера. Для **остановленного** `exec` не работает — сначала `start`.
- `docker stop` / `start` / `restart` / `rm` — остановка, запуск,
  перезапуск, удаление.
- `docker rm` требует остановленный контейнер (`docker rm -f` — сразу,
  с принудительным `SIGKILL`).

### Ключевой факт: когда исчезают данные

```text
stop/start          → данные СОХРАНЯЮТСЯ (файловая система контейнера жива)
docker rm           → изменяемая ФС контейнера УДАЛЯЕТСЯ
новый контейнер из того же образа → «чистая» ФС, ваших данных нет
```

Отсюда правило: **контейнер — плохое место для долгоживущих данных**,
пользуйтесь томами (раздел 6).

## 5. Сборка образов и кэш слоёв (задача 4)

Сборка — это последовательность слоёв, каждый = результат одной инструкции.
Docker кэширует слои и **переиспользует** те, чьи входные данные
не изменились:

- слои выше «точки изменения» → `CACHED`;
- слои ниже → пересобираются заново.

```dockerfile
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y build-essential && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY Makefile main.c ./
RUN make
COPY data/ ./data/
CMD ["./hello"]
```

Практический вывод: **порядок инструкций — это оптимизация сборки**,
а не декорация. Копируйте только то, что нужно, и ставьте часто
меняющееся в конец. `CMD` задаёт команду по умолчанию, `docker run ИМЯ
команда` её переопределяет.

Различайте три понятия: `Dockerfile` (рецепт) → `image` (собранный
результат) → `container` (запущенный экземпляр).

## 6. Где хранить данные: три способа (задачи 6 и 7)

| Способ | Что это | Когда нужен | Живёт дольше контейнера |
|---|---|---|---|
| **ФС контейнера** | write-слой поверх образа | временные, одноразовые данные | ❌ нет |
| **Bind mount** | каталог хоста, подключённый в контейнер | исходники проекта, рабочие файлы, обмен с хостом | ✅ да |
| **Docker volume** | именованное хранилище, управляемое Docker | БД, очереди, логи, любые «свои» данные | ✅ да (пока не `volume rm`) |

### Bind mount

```bash
docker run -v ~/seminar4/shared:/shared ubuntu:22.04 bash   # хост:путь → контейнер:путь
docker run -v ~/seminar4/shared:/shared:ro ubuntu:22.04 ... # :ro — только чтение
```

Слева — путь **на хосте**, справа — путь **внутри контейнера**. Данные
видимы в обе стороны и не зависят от жизни контейнера. Флаг `:ro`
защищает каталог хоста от записи из контейнера.

### Volume

```bash
docker volume create mydata
docker run --mount source=mydata,target=/data ubuntu:22.04 ...
```

Отличие от bind mount: путь на хосте вы **не выбираете** (Docker сам
размещает его, см. `docker volume inspect`), том управляется Docker
(`docker volume ls/inspect/rm`) и переживает пересоздание контейнеров.

Важно: **`docker compose down` удаляет контейнеры и сеть, но не тома и не
bind-каталоги.** Данные теряются только при явном `docker volume rm`
(или `down -v`).

## 7. Docker Compose (задача 8)

Когда в рабочем окружении регулярно нужно запускать несколько связанных
контейнеров, длинная команда `docker run` становится нечитаемой и
невоспроизводимой. Compose выносит конфигурацию в `compose.yaml`:

```yaml
services:
  dev:
    build: .                    # сборка из Dockerfile
    image: demo-hello           # имя образа
    volumes:
      - .:/app                  # bind mount каталога проекта
    working_dir: /app
    command: bash               # команда, удерживающая контейнер запущенным
```

Команды жизненного цикла:

```bash
docker compose up -d     # создать и запустить в фоне
docker compose ps        # состояние
docker compose stop      # остановить
docker compose start     # снова запустить
docker compose down      # удалить контейнеры и сеть (тома остаются)
```

Удобство: конфигурация версионируется рядом с кодом, окружение
воспроизводится одной командой, параметры перестают «теряться в истории
терминала».

## 8. Ресурсы: `--cpus` и `--memory` (задача 9)

По умолчанию контейнер **не имеет фиксированных лимитов** — он свободно
конкурирует с остальными процессами хоста за CPU и память. Ограничения
задаются при запуске:

```bash
docker run -d --name demo-cpu --cpus=0.5 demo-load ./cpuload   # половина CPU
docker run -d --name demo-ram --memory=3g  demo-load ./memload 2
docker run -d --name demo-ram --memory=256m demo-load ./memload 2  # OOM
docker stats --no-stream demo-cpu   # смотрим %CPU / MEM
docker inspect --format 'OOMKilled={{.State.OOMKilled}}' demo-ram
```

Важно понимать:

- `--cpus` ограничивает процессорное время — видно по `%CPU` в `docker stats`.
- `--memory` ограничивает память; при превышении лимита процесс **не
  «замедлится», его убьёт** ядро: `OOMKilled=true`, код выхода `137`.
- Ограничения привязаны к **конкретному запуску** (`docker run`), а не к
  образу: один и тот же образ можно гонять с разными лимитами.
- Кто эти лимиты обеспечивает — **cgroups**, те самые, что дали изоляцию
  из раздела 2.

Зачем это разработчику: воспроизводимое тестирование, честное разделение
ресурсов, защита хоста от «прожорливого» контейнера.

## 9. Типичные ошибки и подводные камни

1. **«Контейнер — это ВМ».** Общее ядро; изоляция через namespaces + cgroups.
2. **Путают `stop` и `rm`.** Данные живут до **удаления** контейнера.
3. **Хранят данные внутри контейнера** — сразу переходить на volumes/bind-mounts.
4. **Порядок инструкций в Dockerfile без понимания кэша** — всё «ниже»
   изменчивой строки пересобирается заново.
5. **`docker compose down` = потеря данных** — нет: тома и bind-каталоги
   остаются.
6. **`--memory` без понимания OOM** — процесс убивает ядро, а не замедляет.
7. **`docker exec` в остановленный контейнер** — сначала `docker start`.
8. **root по умолчанию внутри контейнера** — в продакшене запускают не-root
   (`USER` в Dockerfile), ограничивая capabilities.
9. **Правило «слева — хост, справа — контейнер»** в `-v` путают чаще всего.

## 10. Шпаргалка: ключевые команды по темам

```text
образы:        docker build -t ИМЯ .     docker image ls     docker run --rm ИМЯ
цикл:          docker run -d --name ИМЯ ОБРАЗ команда     docker ps / ps -a
               docker stop / start / restart / rm
внутри:        docker exec -it ИМЯ bash
сборка/кэш:    docker build -t ИМЯ .     (слои выше переменной → CACHED)
данные:        -v ~/host:/in       (bind mount)     :ro — только чтение
               docker volume create ИМЯ   --mount source=ИМЯ,target=/путь
compose:       docker compose up -d / ps / stop / start / down
ресурсы:       --cpus=0.5    --memory=256m    docker stats [--no-stream]
```
