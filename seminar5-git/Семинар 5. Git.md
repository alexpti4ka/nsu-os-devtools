# Семинар 5. Git: системы контроля версий

В ходе семинара вы изучите систему контроля версий Git: устройство репозитория,
три рабочие области, ветвление и слияние, разрешение конфликтов, работу с
историей, исправление ошибок и взаимодействие с удалённым хранилищем.

Практика выполняется на наборе готовых учебных репозиториев, который
разворачивает скрипт `setup.sh` (см. каталог `git-workbench`). Всё выполняется
в выданной на `pglab.nsu.ru` виртуальной машине. Реальный GitHub для
лабораторной не нужен — роль «сервера» играет локальный bare-репозиторий.

> Команды, изученные на предыдущих семинарах, в разделе **«Инструменты»**
> упоминаются только как напоминание. Необычные флаги git ищите в справке:
> `git help <команда>`, `man git-<команда>`.

Все незавершённые на семинаре задачи необходимо закончить самостоятельно.

## Задача 1. Подготовка окружения и настройка Git

### Условие

1. Убедитесь, что установлен git. Если нет — установите его через пакетный
   менеджер. Выведите версию.
2. Настройте личную идентичность, которую git будет подписывать в ваших
   коммитах: имя и e-mail. Используйте локальный (не глобальный) вариант,
   чтобы не трогать общее окружение.
3. Разверните учебный стенд. Создайте рабочий каталог, например `~/gitlab`,
   и запустите там скрипт `setup.sh` из материалов семинара:

   ```bash
   mkdir -p ~/gitlab && cd ~/gitlab
   bash /путь/к/git-workbench/setup.sh
   ```

   После запуска в `~/gitlab` должны появиться `01-basics/`, `02-branching/`,
   `03-history/` и `remote.git/`.

4. Проверьте, что git знает вашу идентичность, и убедитесь, что git не
   использует pager при коротком выводе (по желанию).

### Инструменты

`git`, `apt`, `bash`, `man`

### Самопроверка

Команды ниже работают и показывают ожидаемые значения:

```bash
git --version
git config user.name
git config user.email
ls
# 01-basics  02-branching  03-history  remote.git
```

## Задача 2. Три области репозитория: status, add, commit

### Условие

Перейдите в `01-basics/`. Это обычный каталог с файлами, который ещё **не**
является репозиторием.

1. Инициализируйте репозиторий.
2. Посмотрите, что git «видит» до первого коммита.
3. Добавьте в индекс (staging area) файл `hello.txt`. Повторно посмотрите
   статус.
4. Создайте первый коммит с осмысленным сообщением. Посмотрите статус снова.
5. Объясните своими словами, что произошло с `hello.txt` и `notes.md` в
   каждой из трёх областей: **workspace** (рабочее дерево), **index**
   (индекс/стэджинг) и **storage** (хранение, история).

Сделайте так, чтобы в коммите оказался только `hello.txt`, а `notes.md`
остался неизменённым (вне коммита).

### Инструменты

`git init`, `git status`, `git add`, `git commit`

### Самопроверка

```bash
cd 01-basics
git status            # до add: hello.txt и notes.md — untracked
git add hello.txt
git status            # hello.txt — staged; notes.md — untracked
git commit -m "первый коммит: hello.txt"
git status            # working tree clean, кроме notes.md
git log --oneline     # один коммит
```

Вопрос для себя: почему `notes.md` не попал в коммит?

## Задача 3. История и сравнение: log, diff

### Условие

Продолжите работу в `01-basics/`.

1. Измените `notes.md` (добавьте строку) и создайте второй коммит.
2. Посмотрите историю коммитов в подробном и в однострочном виде.
3. Сравните текущее содержимое `notes.md` с предыдущей версией (diff между
   последними двумя коммитами).
4. Внесите несуществующие изменения в файл, посмотрите `git diff`, затем
   отмените их, чтобы вернуть файл к состоянию последнего коммита.

### Инструменты

`git log`, `git log --oneline`, `git diff`, `git status`

### Самопроверка

```bash
git log                # подробный: hash, автор, дата, сообщение
git log --oneline      # по одному hash + сообщение на строку
git diff HEAD~1        # что изменилось в последнем коммите
```

Вопрос для себя: чем `git diff` (без аргументов) отличается от `git diff HEAD`
и `git diff HEAD~1`?

## Задача 4. Ветвление и чистое слияние: branch, switch, merge

### Условие

Продолжите работу в `01-basics/`.

1. Посмотрите текущие ветки.
2. Создайте новую ветку и переключитесь в неё.
3. В этой ветке внесите изменение в новый файл (например, `feature.txt`) и
   сделайте коммит.
4. Переключитесь обратно на `main` и убедитесь, что изменения ветки там
   пока не видны.
5. Слейте вашу ветку в `main`. Посмотрите историю в графическом виде.

### Инструменты

`git branch`, `git switch`, `git merge`, `git log --oneline --graph`

### Самопроверка

```bash
git branch                     # ветки, * — текущая
git switch -c dev              # создать ветку dev и перейти в неё
echo "новая фича" > feature.txt
git add feature.txt
git commit -m "dev: добавить feature.txt"
git switch main                # вернуться на main
git merge dev                  # слить (fast-forward или merge-commit)
git log --oneline --graph --all
```

Вопрос для себя: fast-forward merge и «настоящий» merge-commit — чем они
отличаются на графике истории?

## Задача 5. Разрешение конфликта слияния

### Условие

Перейдите в `02-branching/`. Здесь уже есть ветки `main` и `feature`, которые
разнообразно изменили одну и ту же строку.

1. Посмотрите историю с ветками и содержимое `message.txt` в `main`.
2. Переключитесь на `feature`, посмотрите, как там изменилась строка, и
   вернитесь на `main`.
3. Выполните слияние `feature` в `main`. Оно завершится **конфликтом**.
4. Откройте `message.txt` — найдите конфликтные маркеры. Уберите их, решив,
   каким должно быть окончательное содержимое строки (допустим любой
   осмысленный выбор).
5. Добавьте изменённый файл в индекс и завершите слияние коммитом.

### Инструменты

`git log --oneline --graph --all`, `git switch`, `git merge`, `git status`,
`git add`, `git commit`

### Самопроверка

```bash
cd 02-branching
git log --oneline --graph --all
git merge feature        # CONFLICT (content) в message.txt
cat message.txt          # видны <<<<<<<, =======, >>>>>>>
# отредактируйте файл, уберите маркеры
git add message.txt
git commit --no-edit     # завершить merge-коммит
git status               # clean
```

Вопрос для себя: что будет, если вместо слияния использовать `git merge
--abort`?

## Задача 6. Исправление ошибок: restore, reset, revert, amend

### Условие

Возьмите каталог `01-basics/` (или создайте новый тестовый репозиторий, чтобы
не терять историю). Проработайте типичные ситуации «я ошибся»:

1. **Опечатка в сообщении коммита.** Исправьте сообщение последнего коммита,
   не меняя содержимое.
2. **Файл добавлен в индекс по ошибке.** Уберите его из индекса, не удаляя из
   рабочего дерева.
3. **Несколько изменений, которые не должны были быть.** Верните индекс и
   рабочее дерево к состоянию последнего коммита.
4. **Коммит, который нужно отменить «честно».** Создайте новый коммит,
   отменяющий изменения выбранного более раннего коммита.

Для каждого подпункта зафиксируйте, какая команда использовалась и что она
изменила в трёх областях.

### Инструменты

`git commit --amend`, `git restore --staged`, `git reset`, `git revert`,
`git status`

### Самопроверка

```bash
git commit --amend -m "исправленное сообщение"   # 1
git restore --staged somefile                    # 2 (убрать из индекса)
git reset --hard HEAD                            # 3 (сбросить изменения)
git revert <hash-коммита>                        # 4 (обратный коммит)
git log --oneline
```

Вопрос для себя: чем `git revert` безопаснее `git reset` для уже опубликованных
(отправленных в удалённый репозиторий) коммитов?

## Задача 7. Работа с удалённым репозиторием

### Условие

Используйте `remote.git/` как «сервер».

1. Из каталога `01-basics/` объявите `../remote.git` удалённым репозиторием
   `origin` и отправьте туда ветку `main`.
2. Посмотрите список удалённых репозиториев и их адреса.
3. Скопируйте (`clone`) удалённый репозиторий в новый каталог, например
   `~/gitlab/myclone`.
4. Создайте в `01-basics/` новый коммит и отправьте его. Затем в `myclone`
   получите изменения (pull/fetch) и убедитесь, что история совпала.

### Инструменты

`git remote`, `git remote add`, `git push`, `git clone`, `git pull`,
`git fetch`

### Самопроверка

```bash
cd 01-basics
git remote add origin ../remote.git
git push -u origin main
git remote -v
# из другого каталога:
cd ..
git clone remote.git myclone
# новый коммит в 01-basics и push, затем в myclone:
cd myclone && git pull && git log --oneline
```

Вопрос для себя: чем `git fetch` отличается от `git pull`?

## Задача 8. Игнорирование файлов: .gitignore

### Условие

Продолжите работу в `01-basics/`.

1. Создайте файл-«артефакт», который не нужно коммитить (например,
   `build.tmp` или файл-лог).
2. Убедитесь, что git видит его как untracked.
3. Создайте (или дополните) файл `.gitignore` и добавьте в него правило для
   этого файла (или для целого каталога/расширения).
4. Убедитесь, что git больше не показывает этот файл.
5. Попробуйте принудительно добавить проигнорированный файл и объясните,
   почему это всё же возможно.

### Инструменты

`git status`, `git check-ignore`, `git add -f`

### Самопроверка

```bash
echo "мусор" > build.tmp
git status                       # build.tmp — untracked
echo "build.tmp" >> .gitignore
git status                       # build.tmp больше не виден
git check-ignore build.tmp       # подтверждает, что файл игнорируется
git add -f build.tmp             # принудительное добавление
```

Вопрос для себя: какие правила в `.gitignore` работают для подкаталогов?

## Задача 9. Анализ репозитория: blame, bisect

### Условие

Перейдите в `03-history/`. Здесь 7 коммитов, созданных тремя «авторами»
(Алиса, Боб, Каролина), и в одном из коммитов заложен баг: сценарий
`test.sh` до этого коммита проходит, а после — падает.

1. **Blame.** Посмотрите, кто и в каком коммите менял каждую строку
   `notes.txt`.
2. **Bisect.** Найдите с помощью автоматического поиска тот самый коммит,
   в который был внесён баг. В качестве проверки используйте `test.sh`
   (exit 0 — хорошо, exit 1 — плохо).

### Инструменты

`git blame`, `git bisect start`, `git bisect good`, `git bisect bad`,
`git bisect run`, `git bisect reset`

### Самопроверка

```bash
cd 03-history
git blame notes.txt            # каждая строка с автором и коммитом
bash test.sh                   # сейчас FAIL
first=$(git rev-list --max-parents=0 HEAD)
git bisect start
git bisect bad HEAD
git bisect good "$first"
git bisect run bash test.sh    # git сам найдёт первый «плохой» коммит
git bisect reset
```

Вопрос для себя: сколько проверок пришлось сделать git при 7 коммитах и
почему это «пополам»?

## Задача 10. Хорошие практики и продвинутые инструменты (по желанию)

### Условие

На любом из ваших репозиториев (лучше — на отдельном тестовом) закрепите
инструменты, которые понадобятся в командной работе. Выберите не менее трёх
подпунктов:

1. **Тэги.** Отметьте текущую версию тегом. Посмотрите теги.
2. **Временное сохранение.** У вас есть незавершённые изменения, но нужно
   переключиться на другую ветку. Сохраните «в ящик» и верните их позже.
3. **Отладка истории.** Посмотрите список всех положений HEAD, включая
   «потерянные» после reset.
4. **Выборочное применение.** Перенесите один конкретный коммит из другой
   ветки в текущую.
5. **Интерактивное переосмысление истории.** Объедините несколько мелких
   коммитов в один.

Также сформулируйте письменно (2–4 предложения):
- как часто делать коммиты и почему;
- из чего должно состоять хорошее сообщение коммита;
- как разумно ветвить командный проект.

### Инструменты

`git tag`, `git stash`, `git reflog`, `git cherry-pick`, `git rebase -i`

### Самопроверка

```bash
git tag v1.0
git stash && git stash list && git stash pop
git reflog
git cherry-pick <hash>
git rebase -i <стартовый-коммит>
```
